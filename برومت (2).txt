2. NON-NEGOTIABLE DEVELOPMENT PRINCIPLES

These rules apply throughout the entire project.

2.1 Functional completeness

- Never create decorative or non-functional controls.
- Never implement buttons that do nothing.
- Never use hardcoded dashboard statistics as production data.
- Never simulate successful financial transactions.
- Never display fabricated records as if they were stored records.
- Never leave critical workflows as frontend-only demonstrations.
- Every implemented action must execute its actual business operation.
- Every displayed financial or inventory value must originate from the correct underlying records.
- All important operations must be validated on the backend or trusted application service layer, not only in the UI.

2.2 Preserve existing functionality

If working inside an existing codebase:

- Inspect the entire existing architecture before modifying it.
- Preserve all existing working features and business rules.
- Never remove, overwrite, or break an existing feature merely to implement a new one.
- Extend existing functionality wherever possible.
- Do not replace established modules without a documented technical reason and explicit migration plan.
- Preserve existing database records.
- Use backward-compatible migrations whenever possible.
- Maintain existing API contracts unless a documented versioned migration is required.
- Do not silently change user permissions, financial calculations, or workflow behavior.

Every modification must include regression tests for affected existing functionality.

2.3 Engineering integrity

- Do not claim that a feature is complete unless it is implemented and tested.
- Do not claim that tests passed unless they were actually executed.
- Do not hide compilation errors, failed migrations, security warnings, or unfinished functionality.
- Do not mark mock implementations as production-ready.
- Do not silently skip requirements.
- Record every important architectural decision.
- Explicitly identify unavailable external integrations and their dependencies.

2.4 No destructive shortcuts

Never use destructive database operations as a convenient development shortcut.

Never delete production tables, reset customer data, replace an existing database, or overwrite imported records without explicit authorization and a verified recovery plan.

16. LICENSING SYSTEM AND COMMERCIAL PROTECTION

The application must not enter its normal operational environment without a valid license or authorized trial.

The licensing system must be controlled by the software developer, not by ordinary customer accounts.

16.1 License types

- Lifetime license.

- Evaluation license.

16.2 License policies

Support configurable limits for:

- Licensed company.
- Number of devices.
- Number of branches.
- Number of users.
- Enabled modules.
- Subscription duration.
- Activation count.
- Expiration date.
- Offline activation policy.
- Grace period.

16.3 License activation

Support:

- Online activation.
- Offline activation.
- Device registration.
- Device replacement.
- Device deactivation.
- License renewal.
- License transfer under developer policy.

For offline activation, use a challenge-response process:

1. Application generates a device-bound activation request.
2. Customer transfers the request to the developer.
3. Developer issues a signed license response.
4. Customer imports the license file.
5. Application verifies the signature and device binding.

16.4 Cryptographic design

Use public-key digital signatures, preferably Ed25519.

- Private signing keys must remain under developer control.
- Never embed the private key in the customer application.
- Embed only the public verification key in the application.
- Sign license payloads.
- Validate signatures.
- Validate expiration.
- Validate device binding.
- Validate license scope.
- Support signed revocation information when available.

Do not claim that licensing makes reverse engineering or software cracking impossible.

Use layered defenses and honest security boundaries.

16.5 Expiration and data safety

When a license expires:

- Display clear expiration information.
- Notify users before expiration.
- Enforce the configured grace period.
- Restrict licensed operational features according to policy.
- Preserve all customer data.
- Do not corrupt or delete databases.
- Provide an authorized data export path where policy permits.
- Do not silently destroy access to customer records.

Implement reasonable protection against local clock manipulation, while documenting the limitations of fully offline time verification.

16.6 Independent developer licensing portal

Build a separate web-based developer portal.

This portal must not be confused with the customer ERP administration panel.

Developer portal features:

- Developer authentication.
- Secure administrative roles.
- Customer management.
- License creation.
- License renewal.
- License suspension.
- License revocation.
- Device activation management.
- Activation history.
- License expiration tracking.
- Product edition management.
- Feature entitlement management.
- License usage statistics.
- Audit logs.
- Secure license signing.
- License download.
- Offline activation request processing.
- Customer support notes.

Store private signing keys securely outside ordinary application databases and source repositories.

Require strong authentication and additional protection for sensitive signing operations.
